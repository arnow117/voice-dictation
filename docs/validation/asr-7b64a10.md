## 已定位的问题

14 条英文空输出全部是 `decoded_chunk_count=0`，没有进入模型。
其原始 WAV 的 RMS 为 0.00047～0.00088，低于生产前置过滤的 0.001 固定阈值。
对 `en-003` 的最小对照保持冻结二进制不变：原音频被跳过；仅在临时诊断副本提高音量至 RMS 0.01 后，
模型解码一次并输出完整英文。该增益副本只用于定位，不进入正式评分。

已要求修正为只跳过数字静音，低音量语音仍送入识别；修正后必须使用原始 120 条重新评分。
数字静音检查不是 VAD，非零环境噪声仍需真实验证。

中文差异主要集中在 `zh-018`：生产运行时输出短文本，与先前 Python 基线差异较大。
同一生产二进制新进程单独复测仍得到同样结果，排除了连续会话积累这一解释。
同版本 Python API 在 1024 和 2048 缓存上限、512 输出上限下均得到完整转写；
缓存上限本身不足以解释两个运行时的差异。尚未据此改变生产参数或声称问题已解决。

进一步用同一静态库的直接 C API 小型诊断程序处理 `zh-018`，1024 和 2048 缓存上限均复现同样短输出，
排除了 Swift 桥接层和这两个缓存值作为单独原因。该对照在两分钟限制内完成，未修改生产代码或模型。
Python 与静态库均报告 sherpa-onnx 1.13.8、Git `11afbd00`、ONNX Runtime 1.28.2；
仅靠版本号不能认定它们的构建行为完全相同。本轮没有继续猜测或修改参数。
